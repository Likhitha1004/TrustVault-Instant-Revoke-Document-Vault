# TrustVault Security Hardening & Verification Report

**Revision:** 2026-11-06  
**Deployment:** Not performed (per owner instruction)  
**Database:** No production database connection, schema migration, or data mutation performed  
**UI:** Existing visual UI preserved

## 1. Code changes applied

### Authentication and authorization
- Public registration now rejects `admin` role assignment. Admin accounts must be provisioned through the trusted bootstrap/recovery path. Public `owner` and `viewer` role selection remains supported to preserve the existing product workflow.
- Access JWTs now carry `typ=access`; API authentication rejects upload-intent tokens even though both token classes use the configured signing key.
- Access-token lifetime reduced from 24 hours to 60 minutes.
- Passwords must be at least 12 characters and no more than 72 UTF-8 bytes. This prevents bcrypt's silent 72-byte truncation from making distinct long passwords equivalent.
- Failed-login throttling added: 10 invalid attempts per 15 minutes per source IP and normalized account identifier. The identifier is hashed in the audit metadata used by the limiter.

### Upload and storage integrity
- Fixed a malformed upload-intent route decorator and restored the missing `return doc` from the standard upload endpoint. Both defects could break runtime behavior.
- Presigned S3-compatible PUT requests now sign the expected `ContentLength` as well as the content type.
- Direct-upload confirmation verifies the signed user-bound intent, object key, declared size, actual stored size, and server-computed SHA-256.
- Confirmed bytes are written under a separate server-controlled final key; the browser's temporary presigned URL cannot overwrite the finalized object.
- Upload validation now examines the actual payload, not just the first few bytes. DOCX/XLSX/PPTX files must have the expected Office Open XML package structure; arbitrary ZIP files and unsafe archive paths/expansion ratios are rejected.
- Bulk deletion endpoint added with per-document owner/admin authorization and audit events. This aligns the implementation with existing test expectations; unauthorized IDs are reported as failures and are not deleted.

### Production configuration and CORS
- Production requires an explicitly configured `SECRET_KEY` (minimum 32 characters) and `CORS_ORIGINS`.
- Production startup rejects wildcard CORS origins and requires exact HTTPS origins.
- Production startup rejects `ALLOW_DEMO_SEED=true`; demo credentials are not seeded in production by default.
- CORS credentials are disabled because the frontend uses explicit bearer Authorization headers, not cookie-based sessions.
- Backend and Vercel serverless API copies were synchronized and compared; security-sensitive modules match byte-for-byte.

## 4. Checks not completed / residual risks

- Frontend production build was attempted but could not complete because frontend dependencies/type definitions (`vite/client` and `node`) were not installed; npm registry access was unavailable. Run `npm ci && npm run build` in CI.
- Real S3/R2 direct-upload integration, provider-specific signed `ContentLength` behavior, bucket policy, private-access settings, encryption-at-rest, and lifecycle cleanup were not verified without cloud credentials.
- Live Vercel/Supabase integration and deployed smoke tests were intentionally not run.
- Dependency vulnerability scanning (`pip-audit`, `npm audit`) was not run because the environment was offline.
- The login limiter is a best-effort shared-database control for repeated attempts from the same source IP/account pair. Add Vercel/edge WAF rate limits for registration, distributed credential stuffing, and broader abuse protection.
- Frontend bearer tokens remain in `localStorage`; an exploitable XSS could expose them. No unsafe HTML sink was found in the reviewed React source, but a stronger long-term design is an HttpOnly Secure SameSite cookie session with CSRF protection and a carefully tested migration.
- File uploads are type/structure validated but are not scanned by an antivirus/malware engine. For untrusted public uploads, add asynchronous malware scanning/quarantine before allowing downloads.
- Review existing production admin accounts; blocking future public admin registration does not automatically demote any admin account already created.

## 5. Required production configuration before any later deployment

- `ENVIRONMENT=production`
- `SECRET_KEY` set to a newly generated random value of at least 32 characters. Rotate any key that may have been used by an earlier build with a hardcoded fallback; this invalidates existing JWTs.
- `CORS_ORIGINS` set to exact HTTPS frontend origins only (comma-separated).
- `ALLOW_DEMO_SEED=false`
- Existing `DATABASE_URL`, `STORAGE_BACKEND=s3`, private bucket, endpoint, and least-privilege storage credentials configured in the deployment secret manager.
- Configure bucket-level block-public-access, encryption, least-privilege IAM, and lifecycle expiration for abandoned temporary objects without deleting `documents/verified/` objects.
- Run frontend build, Python tests with the actual declared dependencies, dependency scanning, and cloud integration tests in CI before deployment.
